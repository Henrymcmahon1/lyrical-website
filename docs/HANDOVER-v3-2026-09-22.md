## 1. The v3 scope and Henry's decisions (22 Sep, evening)

### A. Sign-in: 6-digit email code + Google sign-in
- **Today's failure is a missing key, not the link.** The sign-in action sends its email through
  Resend (`lib/mailer.ts`, `mailCustomer`), and omega has no `RESEND_API_KEY`, so the action returns
  "We could not send the email. Try again in a moment." First fix: Henry puts `RESEND_API_KEY`,
  `ENQUIRY_FROM_EMAIL` (on a domain verified in Resend) and `ENQUIRY_TO_EMAIL` into the omega Vercel
  env. Sign-in will work the same day, before any code change.
- **Then replace the link with a code.** Supabase sends a 6-digit OTP when the email template renders
  `{{ .Token }}` instead of `{{ .ConfirmationURL }}`, and the client does not pass `emailRedirectTo`;
  the site verifies it with `verifyOtp({ email, token, type: 'email' })`. The template lives in
  Supabase Auth settings and needs **custom SMTP** (Resend SMTP credentials) or the built-in mailer
  ignores template edits and rate-limits. Keep the form state: the code screen is the same page.
  (Docs: https://supabase.com/docs/guides/auth/auth-email-passwordless and
  https://supabase.com/docs/guides/auth/auth-email-templates.)
- **Google sign-in** via Supabase's Google provider. Henry creates the OAuth client in Google Cloud
  (redirect URI is Supabase's callback) and pastes client id + secret into Supabase Auth; the site
  adds a "Continue with Google" button on the sign-in page that calls `signInWithOAuth`.
  Rights and licence versions on `profiles` apply the same to either method.
- Migration: existing 183 accounts are email-only; a code sign-in keeps them as they are.

### B. Automatic emails (Henry: "emails are a valuable form of communication")
Henry picked all four: track delivered (and re-roll delivered), welcome + plan confirmation, track
could not be made / refunded, artist EOI received + enquiry acknowledgement. He also asked for **one
folder that holds the email plan, schedule and mock-ups** so it is easy to see: `docs/emails/`
(scaffolded in this commit with the plan; the next session adds the HTML mock-ups and wires them).
- Sending: everything goes through Resend from the website. Triggers:
  - Welcome: first successful sign-in (server action after `verifyOtp` / OAuth callback, once per
    profile, stamp `profiles.welcomed_at`).
  - Plan confirmation: the Stripe webhook after `checkout.session.completed` (paused with Stripe).
  - Track delivered / re-roll delivered / could not be made: the render PC changes `song_jobs`, so the
    website needs a hook. Recommended: a **Supabase Database Webhook** on `song_jobs` UPDATE that
    posts to `/api/hooks/song-job` with a shared secret header; the route checks the transition
    (delivered, rejected) and sends. Alternative: the poller calls the same route directly.
  - Artist EOI received / enquiry acknowledgement: inside the existing enquiry route (the founders'
    notification already exists; the acknowledgement to the sender is the new part).
- Every email uses `lib/email-shell.ts` (brand shell), plain words, one action, no "beta".
- **CONFIRMED 22 Sep (evening):** the **rating reminder is IN scope for v3** (Henry chose "build it
  now"): 24 h after a delivery, if the track is still unrated, send one product email (opt-out,
  respects `/studio/account` preference), max one product email per person per day. This is Bot 1's
  eighth email. Fired by a scheduled check (a Vercel Cron on `/api/hooks/rating-reminder`, or the
  poller), not a drip sequence.

### C. Turnaround time in the studio: **fixed promise per plan**
Henry chose a fixed promise, not a live estimate. **CONFIRMED 22 Sep (evening):** one promise for
every plan: **"usually within 1 hour"**, with the exception line **"up to 3 hours at busy times"**.
(Henry tightened the busy cap from the proposed 24 h to 3 h.) Show it on the plan card, on the

### G. Admin CRM: **build `/admin` on the site over Supabase data**
Research summary: at this stage the things Henry wants to see live in the database, so a custom
admin beats a CRM tool; a tool can be added later for Door 1 deals if relationships outgrow it.
Scope for `/admin` (gated by `ADMIN_PASSWORD` today; move to a Supabase role later):
- People: every account (auth user + profile), plan, credits, tracks this period, sign-in method,
  last seen, licence/rights acceptances, notes and a next action (new tables `crm_notes`,
  `crm_tasks` keyed by user or enquiry).
- Money: subscriptions, credit ledger, Stripe events, refunds (from the tables the webhook writes).
- Work: every job with state, stage timing, failures with the reason (`pipeline_error` is staff-only
  and readable here), re-roll families, deliveries, watermark ids; a re-queue button (writes
  `pipeline_state='queued'`, the poller does the rest).
- Voice: feedback rows with note and tags, filterable, CSV.
- Relationships: enquiries and artist EOIs with status (new, contacted, in talks, signed, closed),
  owner, notes, next action.
- Issues: failed jobs not yet acknowledged, refunds issued, complaints (a `crm_issues` table with
  status), heartbeat age, Supabase storage figure.
- Fold the existing `/queue` tabs into `/admin` so there is one console.

### H. Door 2 copyright detection: **fingerprint at upload and block commercial matches**
Henry's stance. Consequence to state plainly on the pricing and studio pages: a fan cannot make a
version of a commercial recording they do not own; Door 2 becomes "your own songs, or songs you
have the rights to", which is what the doors copy already says. Build: after upload and before the
job is queued, run an audio fingerprint on the vocal and the instrumental (a Vercel route or Modal
function calling the provider), store the result on `song_jobs.copyright_check` (jsonb: provider,
match, confidence, checked_at), refuse the submission with a clear message when a commercial match
is found, log it against the account, and keep the personal-use licence for what passes. Provider:
ACRCloud (14-day free trial, then metered; per-request price is behind their console, so the first
task is to get the real number) with AudD as the fallback (public price $5 per 1,000 requests).
Write the takedown and repeat-offender policy as a page and link it from the terms.
Sources: https://www.acrcloud.com/music-recognition/, https://audd.io/resources/articles/audd-vs-acrcloud.html.
